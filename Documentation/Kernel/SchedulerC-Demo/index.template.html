What Poingo exposed

I made a cute retro bouncing-ball demo called Poingo and showed it off in the SerenityOS Discord channels. It ran fairly well with one ball. Then I turned it up: five more balls, for a total of six bouncing around the desktop. It looked neat, but it stuttered. After a few balls, it started to break down.

Other operating systems could run it on the same hardware. Why was SerenityOS struggling? One thing I truly respect about SerenityOS is that it is simple enough to reason about. I miss that from the earlier days of computing. I also like that it puts the desktop first, instead of being a server OS wearing a desktop hat. I wanted Poingo to run well here, so I dug in.

I found two classes of problems. The scheduler wasn't giving higher-priority parts of the system enough CPU time: WindowServer was getting a little starved by Poingo, and audio started glitching as I added balls.

Then there were the blunt stalls. Poingo would just stop for a few frames. That went beyond scheduling. After investigating and instrumenting the kernel, I traced those stalls to two back-to-back spinlocks in WindowServer.

Both problems need work. This page is about the scheduler.

Start with the Original Scheduler

SerenityOS already has a scheduler. Before replacing it, let’s try fixing it, one problem at a time.

A.1, A.2, and A.3 below are hypothetical repairs. These examples assume one CPU and busy threads that keep wanting more CPU time.

The original

There are 99 priority values and 32 queues, or “buckets.” But an integer arithmetic bug puts priorities 2–99 into the same bucket, leaving priority 1 in the bottom bucket. LOW, NORMAL, HIGH, and MAX all take turns together. Most of the priority control does nothing. The exact arithmetic is below.

A.1: Fix the math

Now the buckets work. Two busy priority-50 threads can shut out a priority-30 thread forever: one runs while the other waits in the preferred bucket. Oddly, just one busy 50 can alternate with the 30, because the scheduler chooses a replacement before putting the current runner back in its queue. The arithmetic bug had been hiding starvation between priorities that shared the broken bucket.

A.2: Compare the current runner too

Keep FIFO turns within each bucket, but include the running thread in the choice. That removes the odd forced alternation. Now a single busy 50 can beat the 30 at every choice and keep running. Starvation gets easier to trigger! The rule is consistent; it just lets higher-priority work shut out lower-priority desktop work.

A.3: Make room for everyone

We could force an occasional turn for another bucket, remembering where we left off and rotating through all occupied buckets. That prevents starvation. But under heavy load, “eventually” can still be a long wait. We now have strict priority with a second scheduling rule bolted on, and an interval to tune. And, we've created a scheduler that is complicated, hard to reason about, and still doesn't lead to a responsive user experience. It has exceptions, and within the exceptions, a virtual second scheduler.

And after all that, different priorities get binned into fewer buckets -- why distinguish at all? 50 and 51 share a bucket and get treated alike, for example, why give expression to the distinction to the programmer if it doesn't MEAN anything?

“Just fix the bugs” naturally grows into a discussion about policy. And once we are deciding how to share the CPU, prevent starvation, and keep the desktop responsive, we’re designing a scheduler -- we should do that deliberately.

Scheduler C

Scheduler C gives every priority its own weight, with no buckets. It runs the thread with the lowest weighted virtual time. Priorities finally affect CPU share, lower-priority threads still get turns, and sleeping threads cannot bank unlimited credit.

That is the proposal: a small set of rules we can explain, inspect, and measure. It still needs real workload evaluation. The demos below show how its policy compares with the unmodified Original Scheduler.

Timer decision: 1,000 Hz. We propose raising the timer frequency from 250 to 1,000 Hz: a scheduling tick every 1 ms. This gives Scheduler C finer CPU accounting and more frequent chances to run newly awakened threads, at the cost of more timer and scheduler work. Both demo panels use this frequency for comparison; the Original Scheduler’s two-tick turn is now 2 ms, and Scheduler C’s one-tick turn is 1 ms.

ORIGINAL SCHEDULER · CODE EXPLANATION

Why do priorities 2–99 all share bucket 0?

The division discards the fractional part before the multiplication happens. The Original Scheduler accepts 99 priority values, but its conversion to a queue index produces only two results: priority 1 goes to bucket 31, and every priority from 2 through 99 goes to bucket 0. This follows directly from the integer expression in the original code.

All source locations below refer to the Original Scheduler at commit 5a4c0d7bd3f5bce844ec45795d90625659a8edf8. They are original repository paths and line numbers, not lines in this JavaScript demo or a later scheduler revision.

The constants and the exact expression

  • Kernel/API/POSIX/sched.h:19 defines THREAD_PRIORITY_MIN as 1; :23 defines THREAD_PRIORITY_MAX as 99. The same definitions also appear in Kernel/API/POSIX/serenity.h:40 and :44.
  • Kernel/Tasks/Scheduler.cpp:44–48 defines ThreadReadyQueues. Its u32 mask is 32 bits, and count = sizeof(mask) * 8 gives 32 queues, indexed 0–31.
  • Kernel/Tasks/Scheduler.cpp:56–66 contains thread_priority_to_priority_index(u32 thread_priority). Line 60 checks the valid range. Line 63 is the faulty conversion. The following is the exact source excerpt from lines 61–65:
constexpr u32 thread_priority_count = THREAD_PRIORITY_MAX - THREAD_PRIORITY_MIN + 1;
static_assert(thread_priority_count > 0);
auto priority_bucket = ((thread_priority_count - (thread_priority - THREAD_PRIORITY_MIN)) / thread_priority_count) * (ThreadReadyQueues::count - 1);
VERIFY(priority_bucket < ThreadReadyQueues::count);
return priority_bucket;

Substitute the numbers, then do the integer arithmetic

Let p be the requested priority. The priority count is 99 − 1 + 1 = 99, and the last bucket index is 32 − 1 = 31. Therefore:

bucket(p) = ((99 − (p − 1)) / 99) × 31
          = ((100 − p) / 99) × 31       ← division is integer division
          = floor((100 − p) / 99) × 31 ← equivalent for these positive values

The numerator and divisor are integers. C++ integer division truncates toward zero, which is the same as rounding down for these positive values. For p = 1, the division is 99 / 99 = 1, giving 1 × 31 = 31. For every p from 2 through 99, the numerator is between 98 and 1: smaller than the divisor 99. The quotient is consequently 0, and multiplying that zero by 31 still gives 0.

Multiplying afterward cannot recover the discarded fraction. For example, at priority 30 the actual expression gives (70 / 99) × 31 = 0; multiplying first would give (70 × 31) / 99 = 21. Those expressions are not equivalent under integer arithmetic. A full-range linear mapping could instead use ((99 − p) × 31) / 98, with multiplication before division and the endpoint span 99 − 1 = 98. That is an illustrative alternative; this demo faithfully runs the Original Scheduler’s expression.

How that becomes the scheduling behavior you see

Kernel/Tasks/Scheduler.cpp:168 calls the conversion when a thread is enqueued; lines 174–178 append it to that bucket and set its occupancy bit. In pull_next_runnable_thread(), lines 73–78 scan occupied buckets starting with the lowest numbered one, then walk its thread list. Thus priority 99 and priority 2 enter the same FIFO queue; neither gets a higher bucket than the other. Buckets 1–30 remain unused by valid priorities.

Priority 1 is the exception: its bucket 31 is considered only after the earlier buckets yield no eligible queued thread. With two continuously runnable, eligible workers in bucket 0 on this single CPU, one stays queued while the other runs, so priority-1 work can starve. These consequences come from the Original Scheduler’s queue mapping and selection order; they are separate from Scheduler C’s weighted virtual-time policy.

FIXING DEFECTS AND CHOOSING POLICY

Not Just a Bugfix!

Why is Scheduler C a proposal rather than a bug fix?

The distinction is between fixing defects and choosing what priority should mean.

Scheduler C fixes real problems, but it also changes scheduling policy. Repairing the original bucket calculation would make different priorities enter different queues. The original selection rule would still prefer the highest-priority eligible queue.

Scheduler C instead allocates CPU service according to weights. A lower-priority thread can run while higher-priority threads remain runnable, because it is owed service under that policy.

A concrete counterexample

Assume one CPU, two permanently busy priority-99 workers, and one permanently busy priority-30 thread, all eligible to run. Repair the Original Scheduler’s bucket arithmetic so that MAX and normal priorities enter distinct buckets, while retaining its bucket-selection policy:

SchedulerWhat happens to the priority-30 thread?
Original Scheduler with repaired bucket arithmetic, retaining its bucket-selection policyIt can receive no CPU time: a priority-99 worker always remains available in the preferred bucket.
Scheduler CIt receives approximately 6.6% of CPU service over time.

Scheduler C’s approximate share follows from its weights:

normal weight = 2,326
MAX weight    = 16,384

normal share ≈ 2,326 / (2,326 + 16,384 + 16,384)
             ≈ 6.6%

Scheduler C’s integer virtual-time charges introduce a small rounding difference. This is a steady-state service-share calculation, not a latency guarantee or a QEMU measurement.

Using two MAX workers makes the example hold even with the Original Scheduler’s exclusion of the current thread: the other MAX worker remains queued. Allowing the current thread to compete would not eliminate this distinction. This example demonstrates a policy difference without depending on that particular choice about the current thread.

The difference is explicit in the source

  • Original Scheduler: choose from the lowest numbered occupied eligible bucket. See Kernel/Tasks/Scheduler.cpp:68–108, particularly the bucket scan at lines 73–78, at commit 5a4c0d7bd3f5bce844ec45795d90625659a8edf8. The arithmetic defect is at line 63, explained in footnote [1].
  • Scheduler C: choose the smallest virtual time, with priority determining how quickly that time advances. See Kernel/Tasks/Scheduler.cpp:29–56 for weights and charging, and :82–108 for selection, at commit e125986328558985179e24b5950f6121fc81ffc0. The enqueue rules at :169–189 retain existing virtual-time debt and raise a waking thread to the runnable floor.

These are original repository paths and line numbers at the stated revisions. The project archive includes the corresponding sources/A-Scheduler.cpp and sources/C-Scheduler.cpp snapshots. Merely correcting the bucket calculation does not introduce Scheduler C’s weights, accumulated service accounting, or wakeup-floor policy.

What this says about the Original Scheduler

The Original Scheduler is compact and its queueing rules are easy to follow. It has served SerenityOS through years of development. The arithmetic bug is real; fixing it exposes a starvation problem in the bucket policy that had been hard to see while most priorities shared one queue.

A.1 through A.3 show why each repair leads to another decision about CPU sharing and desktop latency. Scheduler C is a proposed answer to those policy questions. The intermediate repairs are thought experiments in this demo; the runnable comparison is between the unmodified Original Scheduler and Scheduler C. Real desktop measurements are still needed to judge the proposal.

Scheduler C is a proposed change to priority and fairness policy, motivated by bugs in the original scheduler.

SHARED FOUNDATIONS · SIMPLER RULES

Is this really just Linux's EEVDF?

No. EEVDF first checks which tasks are owed CPU time (their lag), then runs the eligible task with the earliest virtual deadline. Scheduler C simply runs the thread with the lowest virtual time. No lag test. No deadlines. Linux’s EEVDF design.

EEVDF can also use a task’s requested run length to favor short jobs. Scheduler C gives each selected thread a one-tick turn. Both aim for fair CPU service; they make different choices about who runs next.

So, it's really just CFS?

No. Scheduler C takes CFS’s core rule: charge CPU service by weight, then run the thread with the lowest virtual time. Linux’s CFS design.

It leaves out CFS’s actual elapsed-time accounting, ordered tree, variable run lengths, and wakeup preemption. The proposed 1,000 Hz timer gives Scheduler C a scheduling chance every 1 ms and makes tick accounting less coarse. It still is not CFS.

My bet: that core rule plus 1,000 Hz gets SerenityOS roughly 90% of the desktop benefit we want from CFS, with a fraction of the complexity. That 90% is an estimate, not a measurement. We need real input and audio tests to see whether the missing pieces matter.

So what about Poingo?

On Scheduler C, Poingo runs much more smoothly and can run with more balls. There are still brief stalls that I traced to spinlocks. That's a fix for another day.

But this is a move in the right direction. Multiple desktop threads can run without starving WindowServer as much or glitching audio, and the desktop feels smoother overall. I'll upload new videos of Poingo to Discord soon.
